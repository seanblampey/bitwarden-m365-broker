# Bitwarden M365 Broker — Design

Status: approved in conversation, 2026-11-24.

## Intent

Let Claude Code do Microsoft 365 admin work (Exchange Online, Microsoft Graph,
the tenant in general) using admin logins the user already keeps in Bitwarden,
without the password, the MFA code, or the resulting tokens ever entering
Claude's context, transcript, or logs.

Bitwarden is the point: it remains the single place credentials live. The
user does not want to switch to app registrations / certificates.

## Goals

- Claude can say "use tenant X" and then run Graph requests and Exchange Online
  PowerShell cmdlets against it.
- The broker (a local MCP server) reads the Bitwarden login item, signs in to
  Microsoft itself (password + generated TOTP code), holds the tokens, and
  executes calls on Claude's behalf. Claude only ever receives call results.
- The user, not Claude, unlocks the vault and approves any non-read action.
- Which Bitwarden items Claude may use is controlled from Bitwarden itself.

## Non-goals (v1)

- The phone system. To be added later as another item type once the system
  is known (if it is Teams Phone, the Graph/Teams path may already cover it).
- Clicking around admin portals in a browser on Claude's behalf.
- Push / number-matching MFA, SMS, FIDO2 or passkeys. TOTP only.
- macOS / Linux. Windows only.
- Cloud Claude sessions. The broker runs on the user's PC next to Claude Code.

## Anti-goals (a failure even if it "works")

- Any secret (master password, login password, TOTP seed or code, access or
  refresh token, Bitwarden session key) appearing in a tool result, an error
  message, a log file, a command line (visible in process listings), or an
  environment variable of a process Claude can inspect.
- Claude being able to approve its own write actions or unlock the vault.
- Claude being able to widen its own access (add items, edit the allowlist).

## Constraints

- Windows 10/11, Claude Code running locally (CLI or desktop) as the same
  Windows user.
- Honest limit, stated to the user: because Claude runs as the same Windows
  user, the design blocks the obvious paths to secrets but not a deliberate
  attack on the broker process (e.g. reading its memory). Acceptable.
- Password and TOTP seed in one vault makes MFA effectively one factor if the
  vault is compromised. User accepted this trade-off.

## Approaches considered

- **A. Existing Bitwarden logins, broker signs in (chosen by the user).**
  Works with the accounts they already have; full admin rights of that
  account; depends on Microsoft's sign-in page and TOTP-based MFA.
- B. App registration with a certificate stored in Bitwarden. More robust and
  least-privilege, but requires per-tenant Entra setup and moves away from
  using the logins already in Bitwarden. Rejected by the user.
- C. Pass secrets to Claude / env vars. Rejected: fails the core anti-goal.

## Decided design

### Packaging
A Claude Code plugin containing:
- an MCP server (the broker), started by Claude Code over stdio;
- a `PreToolUse` hook that blocks Claude from bypassing the broker;
- a short skill telling Claude how to use the tools.

### Vault access
- The broker drives the Bitwarden CLI (`bw`), already logged in by the user
  once (`bw login`, done by the user outside Claude).
- Unlock: when a vault session is needed, the broker shows a native Windows
  password dialog it owns (not Claude's terminal). The master password goes
  straight from the dialog to `bw unlock` via stdin/env of a child process
  that Claude cannot see; the session key is kept in broker memory only.
  The vault auto-locks after an idle timeout (default 30 min) and when the
  broker exits.
- Allowlist: only items in a Bitwarden folder named **`Claude Access`** are
  usable. Each item is a login with username, password, TOTP seed, and a
  custom field `tenant` (tenant domain, e.g. `contoso.onmicrosoft.com`).
  The item name is the alias Claude uses. Since Claude cannot run `bw`,
  it cannot move items into that folder.
- TOTP codes are generated by the broker from the seed (not `bw get totp`,
  which needs Bitwarden Premium).

### Microsoft sign-in
- Authorization code flow with PKCE against `login.microsoftonline.com`, using
  Microsoft's public first-party clients (Microsoft Graph Command Line Tools
  for Graph; Exchange Online PowerShell for Exchange).
- The broker automates the sign-in page in a hidden browser (Playwright
  driving the installed Microsoft Edge), filling username, password, and the
  TOTP code, then intercepts the redirect to capture the code and exchanges
  it for tokens.
- Tokens and the browser session live in memory only. Refresh tokens keep
  things silent for the session; a second resource (e.g. Exchange after Graph)
  reuses the browser's sign-in cookie instead of re-entering credentials.
- Sign-in failures are reported to Claude as a category ("MFA method not
  TOTP", "wrong password", "conditional access blocked", "page changed"),
  never with page contents that might contain secrets.

### Tools exposed to Claude
- `list_tenants()` — aliases available in `Claude Access` (names only).
- `connect(tenant)` — signs in (unlocking the vault if needed); returns the
  signed-in UPN and tenant.
- `graph_request(tenant, method, path, body?, api_version?)` — Graph call;
  returns status and JSON body.
- `exo_cmdlet(tenant, cmdlet, parameters)` — runs one Exchange Online cmdlet.
  Implemented by spawning PowerShell with the ExchangeOnlineManagement module,
  passing the token over stdin, `Connect-ExchangeOnline -AccessToken`, and
  calling the cmdlet by splatting a parameter hashtable built from JSON
  (never by building a script string). Cmdlet names must match `Verb-Noun`.
  Returns JSON.
- `disconnect(tenant?)` / `lock()` — drop tokens / lock the vault.

### Approvals
- Reads pass through: Graph `GET`; Exchange cmdlets with the `Get-` verb.
- Everything else shows a native Windows Yes/No confirmation dialog with the
  tenant, account, and exact request/cmdlet + parameters. Denial returns
  "denied by user" to Claude.
- User's decision: a plain Yes/No dialog, not Windows Hello. Accepted residual
  risk: a script run by Claude could in principle click it via UI automation.
  Claude's call: the hook also blocks the obvious UI-automation routes
  (SendKeys, UIAutomation, AutoHotkey, wscript), and the dialog defaults to
  "No" and takes focus.

### Output scrubbing
All tool output and errors pass through a redactor that removes the item's
known password, TOTP seed/current code, any JWT-shaped strings, and the
Bitwarden session key before returning to Claude.

### Bypass blocking (hook)
The plugin's `PreToolUse` hook denies:
- shell commands (Bash / PowerShell tools) invoking `bw` / `bw.exe` or the
  `@bitwarden/cli` package;
- reads of the Bitwarden CLI and desktop data directories under `%APPDATA%`;
- edits to the plugin's own files and config.

### Logging
Local append-only JSONL audit log (in `%LOCALAPPDATA%`) of every sign-in,
call, approval, and denial — with secrets never written.

## Calls made after builder review (Claude's, pending user check)

- **Consent:** the broker never clicks through a consent page. If one appears,
  sign-in fails with "needs consent" and the user grants it once per tenant
  themselves. Graph scopes requested: a configurable admin default set
  (directory, users, groups, mail settings, Teams, reports, audit read).
- **One broker per Claude Code session** (stdio). Each session unlocks and
  signs in on its own. A shared daemon is out of scope for v1.
- **Coverage:** v1 is Graph and Exchange Online only. Security & Compliance,
  SharePoint Online admin and Teams PowerShell come later, through the same
  token-and-approval path.
- **Hook coverage widened:** also blocks edits to Claude Code settings files
  (`~/.claude/settings*.json`, project `.claude/settings*.json`) and to the
  plugin's install directory. Obfuscated invocations (string-building `bw`,
  calling it from Node/Python) are an accepted residual risk.

## Account assumptions (confirmed by user)

All target admin accounts: sign in on Microsoft's own page (not federated),
use TOTP MFA with the seed stored in the Bitwarden item, and have no
Conditional Access policy requiring a compliant or domain-joined device.

## Left to the builder

- Language/runtime (suggested: TypeScript on Node, matching the MCP SDK and
  Playwright), project layout, test approach.
- Exact redirect URIs for each Microsoft public client — verify against
  current Microsoft docs; Playwright can intercept any redirect, including
  custom schemes.
- How the native dialogs are implemented (e.g. a PowerShell WinForms helper).
- Idle-timeout and token-refresh details.
- Verification: unit-testable parts (redactor, approval classifier, cmdlet
  validation, hook rules) can be tested anywhere; vault unlock, sign-in, and
  real calls can only be tested on the user's Windows PC against a real
  tenant. The build environment is a Linux cloud container.
